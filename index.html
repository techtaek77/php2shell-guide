01. 일단 PHP가 뭘 하는 애냐?

PHP 서버: 평소에는 멀쩡한데?요청 하나 들어왔을 뿐인데 분위기 왜 이래

웹사이트를 식당이라고 해보자. 손님(브라우저)이 주문서(HTTP 요청)를 보내면, PHP는 주방 직원처럼 주문서를 읽고 필요한 데이터를 정리해요. 이때 작업용 책상, 즉 메모리를 씁니다.

정상적인 경우

주문 → 처리 → 정리

요청을 읽고, 문자열·배열을 만들고, 응답한 뒤 임시 메모리를 정리합니다. 다음 손님에게 깨끗한 작업 공간을 넘겨요.

취약한 경우

정리하다가 사고

요청 처리 도중 메모리가 부족하거나 상태가 꼬였는데, PHP가 이미 버렸거나 제대로 준비되지 않은 자료를 다시 참조할 수 있어요.

핵심 구분: OOM 자체는 곧바로 해킹 성공이 아닙니다. OOM 이후 잘못된 오류 처리가 메모리 손상과 코드 실행 가능성으로 이어지는 것이 문제예요.

02. 작은 요청이 어떻게 메모리를 많이 먹지?

PHP 파서: 요청은 작다며?네트워크 크기 ≠ 내부 메모리 사용량

택배 송장은 한 장인데, 창고 직원이 송장에 적힌 물건마다 상자·분류표·보관 위치표를 따로 만든다고 상상해 보세요. 네트워크에서 받은 데이터 크기와 PHP가 내부에서 만드는 자료구조의 크기는 다릅니다.

📨 바깥에서 보이는 것

HTTP multipart/form-data 요청. 필드 이름, 헤더, 업로드 메타데이터 등으로 구성됩니다.

여기서는 공격용 요청 형식을 제공하지 않습니다.

📦 PHP 안에서 일어나는 것

파서가 문자열, 해시 테이블, 배열, 파일 메타데이터를 할당합니다. 반복되거나 복잡한 필드 구조는 내부 메모리 사용량을 키울 수 있습니다.

PHP의 memory_limit은 PHP 스크립트의 메모리 할당 제한입니다. 예를 들어 128MB라면 특정 작업 도중 그 한도를 넘으면서 할당 실패가 발생할 수 있습니다. 실제 소비량과 트리거 조건은 버전·설정·처리 경로에 따라 달라집니다.

그러니까 post_max_size로 요청 본문을 제한해도 PHP 내부 자료구조의 증폭을 완전히 통제하는 것은 아닙니다.

두 CVE는 별개의 근본 원인입니다. 모든 공격이 두 취약점을 반드시 연쇄적으로 사용하는 것은 아닙니다.

04. 왜 위험한가? 웹사이트 로그인도 필요 없을 수 있음

공격자: 조건만 맞으면...RCE는 자동 성공이 아닌 조건부 결과
1
인터넷에서 HTTP 요청 도착특정 처리 경로는 애플리케이션 로그인 검사보다 앞에서 실행됩니다.
2
PHP 런타임이 요청을 해석Multipart 파싱과 세션 업로드 진행 처리 등이 관련될 수 있습니다.
3
오류 또는 요청 경계에서 메모리 상태가 꼬임불완전한 데이터 참조 또는 해제된 메모리의 재참조가 발생할 수 있습니다.
4
조건이 맞으면 RCE공격자가 PHP 웹 워커의 권한으로 임의 코드를 실행할 수 있습니다. 모든 설치 환경에서 같은 방식으로 성공한다는 뜻은 아닙니다.
클라우드 운영자 포인트: OpenStack 하이퍼바이저가 직접 취약한 것이 아니라, VM·컨테이너·어플라이언스 내부에 포함된 PHP 런타임을 조사해야 합니다.

04-1. RCE가 뭐냐고? 서버가 남의 명령을 듣는 거임 😱

RCE = Remote Code Execution(원격 코드 실행). 해커가 서버에 직접 로그인하지 않고도, 취약점을 통해 서버에서 코드를 실행시키는 것이야.

🍕 피자집 비유로 이해하기

정상 손님: “페퍼로니 피자 주세요.” → 주방은 주문받은 피자를 만듦.

이상한 손님: “피자 주세요”라고 주문했는데, 주문서 처리기의 결함 때문에 주방이 엉뚱한 지시까지 실행한다면? 그게 RCE에 가까워. 주문서(HTTP 요청)는 단순한 데이터여야 하는데, 취약점 때문에 서버가 공격자의 명령처럼 다루는 상황이지.

🧩 PHP2Shell과 연결하면

조작된 HTTP 요청 → PHP 내부 메모리 사용량 증가 → OOM/오류 처리 경로 → 메모리 상태 손상 → RCE 가능성

주의: OOM이 발생했다고 무조건 RCE가 되는 건 아님. 실제 코드 실행까지 가려면 추가 조건과 공격 단계가 맞아야 해.

🆚 DoS와 RCE는 다르다

DoS: “가게 문 닫게 만들기” — 서비스가 느려지거나 멈춤.

RCE: “주방에 들어가지도 않고 요리사에게 내 지시대로 일하게 만들기” — 서버가 공격자의 코드를 실행.

권한도 중요! RCE에 성공해도 무조건 root가 되는 건 아니야. 보통 취약한 PHP 프로세스의 권한으로 실행되고, 추가 권한 상승이 있어야 더 큰 피해로 이어질 수 있어.

🛡️ 그래서 어떻게 막는데?

① 취약한 PHP 런타임을 패치하거나 지원 버전으로 교체 → ② PHP 워커 최소 권한 적용 → ③ 파일·DB 비밀정보 접근 범위 축소 → ④ 네트워크 격리와 이상 징후 모니터링 → ⑤ 이미 침해됐는지 별도 조사.

AI 에이전트에게는 “버전 및 노출 현황 조사 → 수정안 PR 생성 → 스테이징 검증 → 승인 후 배포” 순서로 맡기는 게 좋아. 운영 서버에 무승인 자동 패치는 피하자.

05. PHP 버전별로 어떻게 고치냐?

내가 운영하는 버전을 선택하면 권장 대응을 바로 볼 수 있습니다. 기준일: 2026-10-23. 배포판에서 백포트했다면 PHP 버전 문자열만으로 판정하지 마세요.

🧓 “7버전은 안 보이는데 안전한 거 아님?”

아니요. 패치 목록에 없다는 것은 안전하다는 뜻이 아니라 공식 지원이 끝나 수정 릴리스가 없을 수 있다는 뜻입니다. PHP2Shell의 세부 공격 가능 조건은 버전·SAPI·빌드마다 다르므로 PHP 7.x·5.x 전체에 동일한 RCE가 재현된다고 단정해서도 안 됩니다.

※ 지원 종료 ≠ 해당 CVE 악용 가능 확정. 취약점별 영향 범위와 벤더 보안 공지를 함께 확인해야 합니다. PHP 8.2는 2026년 12월 31일까지 보안 지원 대상입니다.

서버에서 우선 확인할 명령

# CLI PHP 버전: 웹 요청을 처리하는 PHP와 다를 수 있음
php -v

# PHP-FPM 설치/서비스 확인 (환경별 이름 차이 있음)
systemctl list-units 'php*-fpm.service'

# Debian / Ubuntu 계열 패키지 조회
dpkg -l 'php*' 2>/dev/null

# RHEL 계열 패키지 조회
rpm -qa | grep -E '^php|php-fpm'

# 컨테이너는 이미지 내부의 PHP를 별도로 확인
# 예: kubectl exec ... -- php -v (승인된 네임스페이스/파드에서)

배포판, 패키지 저장소, 서비스 이름, 웹 SAPI가 다를 수 있으므로 변경 명령을 무작정 일괄 실행하지 마세요. 서비스가 실제로 사용하는 런타임을 먼저 확인해야 합니다.
